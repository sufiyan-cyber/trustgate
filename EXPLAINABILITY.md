# Explainability

This document explains how the Trust Gate cyber-physical verification agent operates, what information it processes, how it reaches access control verdicts, and what operational boundaries govern its deployment. Any operator, auditor, or participant can understand the system's behavior from this guide without reading the underlying source code.

## Decision and Reasoning: How It Decides
Trust Gate reaches an access control decision by orchestrating six specialized verification stages and synthesizing their structured outputs into one of three deterministic outcomes: PASS, REVIEW, or FAIL. First, the extraction stage parses the presented identity card and validates the credential number against mathematical integrity rules, such as the Verhoeff dihedral group D5 checksum for twelve-digit Aadhaar numbers and Regional Transport Office state prefix rules for driving licenses. Second, the forensics stage computes the Laplacian variance of the document image to verify edge sharpness and detect blur, glare, or digital tampering. Third, the identity matching stage compares the extracted name and date of birth against the event registration record while computing the cosine similarity between 256-dimensional facial embeddings extracted from the ID card photo and the live webcam selfie. Fourth, the liveness stage evaluates physiological telemetry from the MAX30102 pulse oximeter sensor to confirm a real human arterial pulse between 45 and 165 beats per minute with stable waveform regularity. Fifth, the duplicate detection stage queries the SHA-256 cryptographic hash of the normalized ID number against historical check-in records to prevent credential sharing or pass-back fraud. Finally, the decision synthesis engine combines these weighted confidence scores with hard deterministic safety rules: if any critical check fails, the physical gate remains locked; if any check is inconclusive or low-confidence, the session is routed to a human organizer for manual review; and only when all identity, liveness, and eligibility checks succeed does the system issue an OPEN_GATE command to the physical servo turnstile.

## Input, Data Source, and Data Used
Trust Gate ingests four primary categories of input from optical sensors, embedded hardware peripherals, and local registration records during a verification session. The first data source is the high-resolution document image captured via the kiosk webcam or uploaded file, from which the agent extracts the participant's full name, date of birth, issuing institution, and credential identifier. The second input is the live participant selfie frame captured from the built-in camera, which is converted into a 256-dimensional numerical feature vector for biometric face comparison without retaining invertible facial templates. The third data source is real-time hardware telemetry streamed over USB serial from the ESP32 microcontroller, including infrared approach detection, capacitive touch contact, and MAX30102 photoplethysmography (PPG) red and infrared pulsatile waveform measurements. The fourth input is the local SQLite or PostgreSQL registration database, which provides the pre-registered participant profile, age eligibility rules, and one-way SHA-256 document number hashes from prior sessions. To uphold strict data governance and privacy compliance, raw government identification numbers are never written to disk in plaintext; they are immediately masked to their last four digits for display and hashed via SHA-256 for duplicate lookup.

## Limitation, Constraint, and Known Issue Analysis
Trust Gate operates under strict physical, optical, and algorithmic constraints that operators must account for during live deployment. A primary limitation is that optical document extraction and facial embedding comparison depend on adequate ambient lighting and camera focus; severe motion blur (Laplacian variance below 65.0) or specular glare on laminated cards will lower extraction confidence and trigger a manual REVIEW verdict rather than automatic entry. Another constraint is that the Verhoeff D5 mathematical checksum and RTO format validators prove the structural and mathematical validity of a government ID number offline, but they do not query restricted government citizen databases such as live UIDAI biometric vaults unless an authorized DigiLocker API gateway is provisioned. Furthermore, a known issue in live hardware mode is that the MAX30102 optical pulse sensor requires steady fingertip contact for four seconds; excessive finger movement, cold peripheral circulation, or an unplugged USB serial port will cause the liveness check to report an disconnected or unstable signal and keep the physical servo gate locked. Finally, when both cloud language model providers (Groq and Google Gemini) experience network outages or quota exhaustion, the agent automatically degrades to its local deterministic rule engine and OpenCV computer vision fallback, which preserves physical security guarantees but produces template-based audit summaries instead of natural-language narratives.
